# Changelog

## Unreleased

**The largest release auditorr has had, and almost all of it is one idea.**
Every workflow that can delete, hardlink or replace a file was reviewed end to
end, and most of what came out shares a single root cause: auditorr could not
tell *"your client says nothing claims this file"* from *"auditorr could not
ask"*. Both arrived as an empty answer — and an empty answer is what makes a file
look orphaned, a title look absent from your library, or a cross-seed look like
it does not exist. Acting on it deletes things. The fixes run from the
torrent-client layer up through every page that has a button on it, and the rule
throughout is that absence of evidence is reported as absence of evidence.

Nothing here needs a configuration change and nothing is migrated: an install
that upgrades keeps its database, and the first scan after upgrading rebuilds
what the new pages read.

With thanks to **essentrix83** (issue #17 and their fork) and **Joloxx9**
([#24](https://github.com/thrill-burn/auditorr/pull/24)), whose findings are
credited in the entries below, and to the reviewer whose 2026-09-10 read of the
workflow code found eleven more.

### Safety

Everything in this section could cost you data, or already has. Ordered by what
happens to your files rather than by which part of auditorr was at fault.

#### Silence was read as an answer

- **A torrent client that answered badly could get your whole torrent folder listed as orphaned** — "orphaned" is not something auditorr reads off a file. It means *no torrent in your client claims this path*, and it was worked out from one snapshot of the client's answer, with no way to tell "your client says nothing claims this" apart from "your client didn't answer". A per-torrent file listing that timed out came back as an empty list, so every file of a live, seeding torrent turned up in **Cleanup** with a green *frees X* beside it. A client that answered with no torrents at all — a rebuilt container with a fresh session directory, a restored config pointing at an empty profile, or simply a scan landing while qBittorrent was still loading its session — was believed absolutely, and the entire torrent tree was rendered as orphans under a single *Select all*. Nothing stood between that and a delete script. A failed listing is now recognised as one, and the torrent's files are located on disk instead, so they stay claimed rather than defaulting to orphaned. **A scan whose view of the client is implausible — far fewer torrents or files than the last scan, instances that didn't answer, or nothing at all while your torrent folder is full — refuses to save anything.** Your file lists, health score and change log keep describing the last scan that completed, and the reason is shown; if the drop is real, running a scan manually accepts it. Throughout the torrent-client layer, an unanswerable question now looks different from a negative answer.
- **A torrent listing that stopped short was taken for the whole client** — qui hands over its torrents a page at a time and says how many there are in total. auditorr stopped at the first short page without ever comparing the two, so an instance that returned three of your torrents when it had said it had three thousand was treated as having answered completely — and every torrent missing from that answer was classified as orphaned, with its files offered for deletion. A listing that can't be shown to be complete is now a failed instance, which the scan refuses to save, Cleanup refuses to build a delete script from, and Trumped refuses to resolve a group with.
- **With several qui instances, one that didn't answer left the others looking like the whole picture** — the Trumped workflow's group resolution asks your client for every torrent it knows. If an instance failed, that was logged and the listing carried on, one instance short, indistinguishable from a complete one. A cross-seed group built from it silently loses every member living on the instance that stayed quiet — and confirming the swap deletes the payload those members are still seeding. auditorr now refuses an incomplete listing rather than acting on it. (qBittorrent already behaved this way; the two backends disagreed.)
- **A qui scan that hit its five-minute per-instance ceiling saved the partial answer as truth** — it warned to the log and nothing else, so nothing in the app or the debug report said the scan had only seen part of your client. The unanswered torrents are now located on disk like any other failed listing, and the incompleteness is recorded where the scan can act on it.
- **A failed tracker lookup threw away a perfectly good file listing with it** — both calls shared one catch-all, so a tracker request timing out on an otherwise healthy torrent discarded its file list as well, and its files read as orphans on the strength of an entirely unrelated failure.
- **Removing a torrent could delete files a second qui instance was still seeding** — the same torrent can be added to two qui instances. auditorr's live view of your client kept only the first one it saw and dropped the other without a word, so when you removed the torrent from one instance in Triage, nothing told the removal that the other instance was still using the files, and they were deleted with it. Each instance's copy of a torrent is now its own registration: the other one keeps the files, and a request that doesn't say which instance it means is refused rather than guessed.
- **A drive that wasn't mounted could be saved as an empty library** — auditorr decides what is orphaned, and what is unseeded, by joining your torrent client's answer to what it finds in your torrent and media folders. A folder that wasn't there walked as an empty one, with a log line and nothing else: a missing media folder saved **every torrent as not imported** — filling Triage, dropping the health score and writing all of it into the record — and a missing torrent folder saved your **whole library as unseeded**, filling Backfill. The realistic way in is a container that starts before the array or a network share has finished mounting. A folder that is missing, or one whose category or release folders can't be read, now refuses the scan instead, and says which of the two it is and what to fix; a folder that is there but has suddenly lost most of its files is refused the same way a torrent client that forgets its torrents already was. A folder that is simply empty on a fresh install still scans — there is nothing to protect yet. At startup, a missing folder is retried at one, two and five minutes before it is recorded as a failure.
- **A Sonarr that answered for most of your library looked like one that answered for all of it** — Sonarr needs one request per series, and a series that times out is deliberately skipped so a single failure can't discard the instance. But the survivors came back as a plain list, so forty missing series out of four hundred were indistinguishable from four hundred series with no files, and every episode underneath read as *Import Pending* or *Not in Library* — inviting a rescan of files that are fine, or worse. Partial reads are now reported wherever a full failure is: Triage, Backfill, and the Test button in Config, which no longer prints a file count it knows to be short.

#### Files deleted that something still needed

- **Removing a torrent from Triage could delete files a cross-seed was still seeding** — **Remove from client** deletes each torrent's files unless it finds another torrent still using them, and it "found none" in three situations where it had never looked: when your client didn't return the torrent's own file list, when it didn't return a neighbouring torrent's, and when the neighbour was a different size — a cross-seed carrying one extra `.nfo` is a few bytes larger, and only torrents of *exactly* the same size were checked. That last shape is worst on a **Dead Registration** row, whose files belong by definition to a working cross-seed: removing the dead registration could delete the file the cross-seed was seeding. Files are now deleted only where auditorr has established that nothing staying in your client uses them. Torrents are compared by the files they hold, not by size, and a cross-seed of a cross-seed counts. Wherever auditorr couldn't check, the torrent is removed and **its files are kept**, and the dialog says so before you confirm; the worst that leaves is an orphaned file, which Cleanup checks against your client again before it will delete anything.
- **Trumped could delete a payload out from under a cross-seed it had missed** — a trump removes every torrent standing on the old release *with its files*, and the set it removes is worked out for you: you confirm the torrent you recognise, and auditorr adds every cross-seed sharing its files. Three things could quietly leave one out, and a left-out cross-seed stays registered on top of files that no longer exist. A cross-seed whose file list timed out was simply skipped, and the page showed a smaller group as if it were complete. A cross-seed carrying one extra file — a tracker-required `.nfo`, a different sample — was ruled out before its files were even looked at, because only torrents of *exactly* the same size were considered. And a torrent sharing files with a cross-seed, but not with the torrent you picked, was never considered at all. Membership is now decided by shared files alone, followed all the way through; a group auditorr couldn't fully check says so, and removing it needs you to acknowledge that first. A torrent client instance that doesn't answer still stops the swap outright, because a cross-seed living there is invisible rather than merely uncounted.
- **Trumped now checks whether your library still holds a copy before it deletes anything** — the confirm step said *"your library hardlinks survive"*, and that sentence was the whole reason deleting files was safe; nothing checked it. It is false whenever the trumped release was never imported, was imported by copying, or has since been upgraded — on the reference setup, one torrent file in thirty. Every torrent in the group now shows whether a link to its files exists outside the group (normally your library copy), **could not check** where auditorr couldn't see the file, or **only copy** — in which case removing it asks again, in a dialog that names how much data will be destroyed. The server enforces the same rule, so a stale page can't skip it.
- **A Trumped swap re-checks the group at the moment it deletes** — the list of torrents to delete was whatever the page had resolved, possibly many minutes earlier. A cross-seed script adding a registration while the page sat open, or a torrent rechecked into a different folder, still went into a delete with files. auditorr now resolves the group again immediately before deleting, and if anything has changed — a torrent gone, one no longer sharing the files, or a new one joined — nothing is removed and you're sent back to confirm the group again.
- **Triage's remove dialog had stopped finding cross-seeds** — since the previous release it failed whenever a selected torrent was in your client, printed *"no cross-seeds"* under every row, and still let you remove, with files deleted by the rule above. It works again, and if it can't check, it says so instead of implying there's nothing to find.
- **What the remove dialog shows is what happens** — auditorr checks the cross-seed groups again the moment you confirm. If anything moved — a cross-seed appeared or went, or a torrent shown keeping its files would now have them deleted — nothing is removed and the dialog shows you the new answer. A change towards keeping files goes ahead, and the result says so.
- **Triage said "Not in Library" when it had simply failed to ask Sonarr/Radarr** — that verdict means *no arr has ever heard of this title*, and its description ended *"junk can be deleted"*. It was reachable when no arr answered at all: a failed library fetch came back as an empty list, "Sonarr/Radarr configured" is read off your settings rather than off the request, so no warning fired, and every row on the page fell to the one bucket that invites a delete — on files that, being not-imported, are the only copy you have. A new **Could Not Check** bucket now takes those rows instead, the instances that didn't answer are named at the top of the page, and the verdict that means "nothing knows this" is unreachable while something couldn't be asked. Rows that *did* match are unaffected: this suppresses a conclusion drawn from silence, not evidence auditorr actually has.
- **A Cleanup delete script now checks your torrent client again before it is built** — "orphaned" means *no torrent in your client claims this file*, and that was decided by the last scan, which can be hours old (and is deliberately older while you work through a workflow page). In that gap a cross-seed tool can inject a torrent for exactly those files, you can re-add and recheck a torrent, or a torrent added while the scan was walking your disk can land — and the script would delete its data. The script can't check this itself: it runs on your host, usually without your client's credentials. So when you click **Generate Delete Script**, auditorr asks your client about the selection right then. Any file a torrent claims now is left out, and both the dialog and the script's header say how many. If your client — or any qui instance — doesn't answer, no script is built at all. The script is stamped with the time it was checked and warns you if you run it more than a day later.
- **Cleanup could present the last copy of your data as safe, and couldn't see half of a cross-seed** — a file hardlinked at two places in your torrent folder, both torrents gone, is still the *only* copy of that data; deleting both paths destroys it. Cleanup listed just one of the two paths (the other could never be cleaned up through the page at all), and its only safety marker meant "the media library has a link", so a link anywhere else — a manual hardlink, a snapshot — was invisible. Every file now carries a state read off the disk at scan time — **library copy**, **linked elsewhere**, **only copy**, or **could not check** — and a cross-seeded file is one row listing all its paths, counted once.
- **The delete script reported files it failed to delete as deleted** — `rm` wasn't checked, so a read-only mount, a permission error or an immutable flag printed `✓ Deleted`, counted the space as freed, and then blamed "concurrent activity" when the disk hadn't changed. Failures are now their own **FAILED** count, never counted as freed, and the script exits non-zero. A file whose name starts with `-` is also deleted rather than read by `rm` as an option.

#### The wrong file replaced or linked

- **Backfilling one episode could replace the whole season and orphan every torrent behind it** — Backfill searched every TV candidate as a **season pack**, however much of that season you were already seeding. Pick one unseeded episode out of ten, grab the result, and the whole season downloaded; because a backfill is rarely an upgrade, Sonarr parked the import, and auditorr then forced it through over *all ten* episodes. Nine library files hardlinked to torrents you were seeding were replaced, all nine of those torrents became orphans, and your health score fell on two counts at once — the direct result of running the workflow whose whole point is the opposite, with nothing having gone wrong. A season is now searched as a pack only when every episode file Sonarr holds in it is unseeded, which is the case a pack is genuinely right for: nothing it replaces was being seeded. Otherwise each episode is searched on its own, and an episode row never offers a season pack or a multi-episode release, even though an episode search can turn one up. The rows say which they are: `S01 season pack · 10 ep`, or `S01E05`.
- **Backfilling a two-episode file could delete one of its episodes, and an episode row could be offered another season's episode** — Backfill offered an episode's row any release covering *some* of the file's episodes, so a file holding S01E01 and S01E02 was offered an S01E01 release, and the import that followed was allowed through too. Sonarr replaces the whole existing file when it imports an upgrade, so grabbing it deleted the file behind E02 and left the torrent seeding it orphaned. Separately, Sonarr describes a release's episodes by number with the season kept apart, and auditorr read the numbers alone, so an S02E05 release, or the special S00E05, was offered for S01E05, and an S02 season pack for an S01 row. A release must now cover exactly the episodes of the file it replaces, in the same season, and an import that names only part of a library file's episodes is never forced in. Found by assessing the 2026-09-10 outside review's first design amendment against the shipped season-pack rule.
- **Backfill's forced import could move files out from under seeding torrents, or re-import the file it was replacing** — when Sonarr or Radarr parked a backfill's import, auditorr forced it through with no limit on what it imported, in the arr's default mode — which *moves* the files whenever the arr isn't tracking the download itself. And when the arr didn't say where the download was, it fell back to your library folder, whose only file is the one being replaced. A forced import now only ever touches the episodes that row was for, always copies (a hardlink, when your arr has hardlinks turned on), and stops and tells you when it can't tell where the download is or which episodes it covers, rather than guessing. The same copy-not-move rule now applies wherever auditorr forces an import from a folder.
- **Dedupe could hardlink two half-finished downloads together and corrupt both** — auditorr knew what your client was *doing* with each torrent (seeding, downloading, paused) but never whether the payload was actually finished, and the two are not the same question: a **paused** torrent at 40% and a paused torrent at 100% are the same word. So an unfinished file was a duplicate candidate like any other. qBittorrent doesn't pad files out as it goes — it writes **sparse** files, which report their full final size while the parts not yet written read as zeros. Two unfinished files of the same size whose written parts don't overlap therefore look identical: same size, same quick fingerprint, and they **pass the `cmp` check in the generated script**, because at that moment both really are zeros in those places. The clean case is two torrents queued at 0%, which are genuinely byte-identical. The script hardlinks them, two torrents write into one file, both are ruined, and there is nothing to recover from. `cmp` is the last line of defence for every other way Dedupe can be wrong, and it is no help here — so nothing your client hasn't confirmed as finished is a duplicate candidate any more, including anything it gave no straight answer about. A missed reclaim costs disk space; the alternative costs two torrents.
- **Dedupe could trade two files' paths instead of linking them** — when one copy of a duplicate was hardlinked into your library, the pair showed up as two groups, and the script linked each copy onto the other: the first copy's torrent path ended up on the second copy's data, and the second's on the first's. Nothing was freed, and both torrents stopped reading as imported, so your health score fell. A group is now one set of identical files — every path of each file listed together — and nothing is ever linked in two directions. (The redundant groups were first reported by essentrix83, in their fork, as reciprocal aliases.)
- **A failed link could delete the file it was meant to replace** — the script used `ln -f`, which removes the destination before it finds out the link can't be made. That can happen on a pooled filesystem that refuses a link between two of its drives, which all report the same disk: the copy was gone, and nothing replaced it. The script now makes the new link under a temporary name beside the file, checks that it really is a hardlink of the kept copy — a pooled filesystem can answer a link with a copy or a symlink — and only then renames it over the original, so nothing is removed before its replacement is in place and no path is ever missing. Found by essentrix83 (issue #17 and their fork).
- **Relinking part of a file broke its import** — a file hardlinked at more paths than auditorr lists (a cross-seed's second path, a snapshot) had only the listed path replaced. That frees nothing and splits the file, which for a torrent file and its library copy means the torrent stops reading as imported. The script now counts each file's hardlinks before touching it and leaves alone any file it can't replace completely. Space counts as freed only when a file's last link is replaced, and a run that stops part-way through a file finishes it the next time.
- **Dedupe could change who can read a file** — every path of a hardlinked file shares one owner and one set of permissions, so linking a copy gave its path the kept copy's. Where qBittorrent, Sonarr/Radarr and Plex run as different users, that could lock one of them out of a file it used to read. A copy whose owner or permissions differ is now reported and left alone.
- **A double-submitted trump grabbed the replacement twice, and a failed grab left you with nothing** — Trumped removed the old torrents with their files first and grabbed the replacement second, so a grab that failed after the removal reported success at removing and left you with neither the old release nor a new one. It now grabs first and removes only once Sonarr/Radarr has accepted the grab; a failed grab removes nothing, and a removal that fails after a successful grab tells you the replacement is on its way and the old torrents are still in your client. The group is also re-checked between the two, because a replacement saved onto the same files joins the group — removing it with its files would delete the replacement. And every execute is now one operation: clicking twice, or retrying a request that never answered, runs it once and replays the first answer, where the second click used to be a second download (the queue check in front of it only sees a download the arr has already queued).
- **"Imported successfully" for an import that never happened** — after a grab, auditorr follows the download into Sonarr/Radarr. The follow-up reported success for five different things, because each of them ended as an empty answer: a queue it couldn't read at all, a download that never appeared, a download that **failed** in the arr, one that was removed, and a genuine import. Backfill rows and the import panel showed a green tick for all of them. Success now means one thing — the arr's file for that movie, or for the episodes that row was for, actually changed — and every other ending says what it was instead. As part of this, a download **still in progress** is never force-imported: after the two-hour wait auditorr used to force the import of a file that was still being written, three times. And where your indexer supplies an info hash, it is used to tell this download apart from another download of the same series in the queue, which could previously stand in for it.

#### Files hidden from auditorr's own view

- **One click in Cleanup could hide your entire media library from auditorr** — Cleanup groups orphaned files by release folder, and a single-file torrent saved straight into a category directory (`movies/Film.2020.1080p.mkv` — what qBittorrent does by default for single-file torrents) has no release folder. Every such file in the category collapsed into one group called `movies`, with a header checkbox that selected all of them, and *Exclude* then wrote the rule `movies/`. A trailing slash means "this subtree", and the match runs against both of auditorr's walks — so that rule excluded the **media library** as well as the torrent folder. Everything under it stopped being scored, the health score jumped, Backfill emptied, and File Explorer hid it, while the toast read *Added 1 exclusion rule*. Groups that aren't a release folder are now labelled **loose files** and only ever produce one rule per file. (Recoverable if it happened to you: the rule is visible and editable in Config → Excluded Files & Folders.)

- **Excluding a Cleanup folder could hide a torrent that was still seeding** — Cleanup offered to exclude a whole release folder whenever the folder was deep enough, and never checked what else lived in it. One stray file inside a live torrent's folder — a sample a repack left behind, an old `.nfo` — made a one-file group whose **Exclude** wrote a rule for the whole folder, taking the seeding torrent's files out of scoring, the hardlink figure and Backfill. auditorr now offers a folder rule only where every file under the folder is orphaned — including a live cross-seed's second hardlink, which sits on no file record at all — and the folder isn't a category directory shared with your media library. Where it isn't safe, the group says why and excluding writes one rule per file.
- **A Sonarr/Radarr outage could be forgotten between two requests** — Triage's *Could Not Check* bucket exists so that "no arr answered" can never read as *Not in Library*, whose files are the only copy. The failure and the library it described were stored separately, and with several requests in flight a successful refresh landing between the two left one request holding an empty library and no failure — and *Not in Library* back. The two now travel together. Trumped reads them the same way.

- **A file caught halfway through a move was reported as a duplicate, an orphan, and 3.5 GB you could reclaim** — delete a file that a process still has open and the filesystem can't free it, so it renames it out of the way and drops that name when the last handle closes: FUSE (which is what Unraid's user shares are) uses `.fuse_hiddenXXXXXXXX`, NFS uses `.nfsXXXX`. **The file has already been deleted; what's left is the filesystem's note that it hasn't finished.** On the reference setup Unraid's mover copied a 3.5 GB episode from cache to the array and couldn't unlink the source because qBittorrent had it open — so one file mid-move appeared as two, on two different disks, and every workflow with an action offered to do something about it. **Dedupe** picked the *tombstone* as the copy to keep and would have replaced a real file with a hardlink to a name being removed (`cmp` can't catch that — the two are the same file). **Cleanup** offered it as an orphan worth 3.5 GB, where deleting frees nothing, because the handle owns the file rather than the name. **Triage** lost the one-rule exclusion for the release folder it sat in. And it counted against your health score and your Sentinel streak. Not one of those actions would have helped: a tombstone goes when the process closes the handle, and nothing auditorr generates can hurry that. They are now ignored everywhere, on every install, without configuration. They remain visible in File Explorer marked as excluded, and in Cleanup's Excluded count, so nothing is hidden from you — they're just no longer treated as media.


#### A half-finished picture saved as the truth

- **An interrupted scan could leave half of one audit and half of another** — a scan saved its results in sixteen separate steps: the file lists, the health score, the change log, the upload history, your Rounds progress and more, each on its own. If saving failed part-way (a full or read-only data volume), everything written before the failure stayed. Your torrent list could then belong to one scan and your media list to the one before it, so a file read as **unseeded in Backfill and not imported in Triage at the same time**; and because the upload history and the change log were written *first*, the next scan measured itself against entries for a scan that never finished saving — a spike in the upload chart, or every file reported as coming back. A scan now saves everything in one step: it all lands, or none of it does and the last complete scan is left whole, with the run recorded as an error that says so.
- **A workflow page could combine two scans** — Dedupe builds its groups by reading your torrent list and your media list and joining them, and the Config page's health-score refresh reads both and **saves the result back**. A scan landing between those two reads handed the page one list from each: Dedupe could show a group that never existed, and saving Config could store a health score built from two different scans until the next one ran. Pages that read more than one list now read them all from the same scan. Cleanup and Triage read theirs the same way.

#### Generated scripts

- **A file name could run a command inside a generated Dedupe script** — the same hole Cleanup's script had: file names, and the configured folder path, were written into `#` comment lines raw, and a newline ends a comment. Nothing path- or config-derived reaches a comment unescaped any more. (Reported by the 2026-09-10 outside review as S10.)
- **A file name could run a command inside a generated delete script** — the script wrote each file's name into a `#` comment line, and a newline ends a comment, so a file whose name contained one turned the rest of its name into a command in a script you were told to run. Nothing path-derived reaches a comment unescaped any more.
- **An empty selection generated a script for every duplicate group** — posting no groups, or opening the script's address directly, built a script for all of them. A Dedupe script is now only built for groups you selected, as Cleanup's already was.

### Improvements
- The debug report gains a **source health** section: how completely your client could be asked on the last scan, and why a scan refused to save its results if one did. It now also counts the torrents your client says aren't finished, and any it gave no usable completion figure for.
- **Dedupe reclaims cross-seeded copies instead of leaving them alone** — the script replaces every path of a file or none of them, and it counted a file's hardlinks before touching it precisely so it could refuse the ones it couldn't replace whole. But auditorr only recorded *one* path per file in each folder tree, so a copy cross-seeded into two tracker directories looked like a file with a hardlink auditorr had never seen, and every group where more than one copy was cross-seeded was left alone: correct, and nothing freed. Each scan now records every path a file has in your torrent and media folders, so those groups link and the space is actually reclaimed. A copy that really does have a link auditorr can't see — a snapshot, a backup tree, or a path hidden by an exclusion rule — is still left alone, exactly as before. **Found and fixed independently by [Joloxx9](https://github.com/Joloxx9) ([#24](https://github.com/thrill-burn/auditorr/pull/24)), against the previous release, where the same gap split the file and claimed the bytes anyway.**
- **Text on the workflow pages now follows one type scale** — Backfill, Cleanup, Triage, Dedupe and Trumped (and the script and Import Jobs panels that open over them) sized their text with hardcoded numbers, most of which weren't on the scale the rest of the app uses; half of them sat exactly between two of its sizes. Every piece of text is now sized by what it *is*, so the same kind of text is the same size on every page: section headers agree with each other, the paragraph under a page title matches the prose beneath it, and readouts like sizes, counts and ages are one size rather than four. The most visible change is **status tags and badges — the quality, HDR, match, tracker and verdict chips — which were 9, 10, 11 and 12px and are now all 11px**, so the smallest text on the busiest pages is easier to read. A few release names in Trumped's lists now wrap onto one more line as a result; they have always wrapped rather than truncate, because the release name is the thing you're checking.
- **Warnings, alerts and errors outside the workflows render as boxes again** — the same dropped-colour bug was on the rest of the app: the error banner across the top of every page, the dashboard's threshold alerts and their *View* buttons, Audit History's load error, Config's "every weight is zero" warning and the Sidebar's scan-error box were all drawn as loose coloured text with no box around them. Selected options and search fields that hold a value get their faint highlight back, in Config, the file browsers, Audit History, Trackers and the setup wizard, and the score chart finally draws its line under the point you're hovering. Row tags (*orphaned*, *seeding*), the *Open in Sonarr/Radarr* actions, the sidebar's counts and Config's run badges stay as coloured text rather than becoming filled pills: that is how they have always looked, and a pill on every row of a long list is a lot of colour. A test now fails the build if the broken colour spelling comes back anywhere in the frontend.
- **The workflow pages share one set of buttons and one heading style** — every workflow had grown its own buttons: seven different paddings, five corner radii, two weights, and white text on orange in one place where everywhere else used dark. None of them responded to hover. They are now one button in three sizes — page-level actions, small controls, and the chips inside a row — with a hover state, and Rounds' *Open …* buttons are the same button. Headings follow Triage's: a section heading is bold, a sub-heading semi-bold, and an item's title medium, so Cleanup's and Dedupe's folder and file names no longer outweigh the heading above them and Backfill's section labels stand apart from their sub-labels. Also tidied: the results screen of a Backfill search centred its "Workflows" label while everything under it was left-aligned; Trumped's *Confirm & find cross-seeds* stretched into a full-width orange bar; and the empty-state 🎉 is now a simple check icon. Backfill's Release Ranking, Priority and Search Depth choices are now one kind of card at one width, so the three rows line up — Search Depth was a taller box around a large number, and the others were each as wide as their own words — and with no candidates the *All* choice no longer offers 999.
- **Every filter in auditorr is one control, and every button one of two heights** — with the colours drawing properly, a pill and a button looked equally clickable, and there were fifteen shapes doing five jobs: File Explorer alone had Status as pills, View and Sort as bordered pairs doing the same job four controls along, a third shape for Duplicates and Excluded, and controls at four heights in one toolbar. It now tells you to fix the instance, the path mapping, the mount or the permissions, and only offers acceptance where accepting is the right answer. The debug report gained the reference counts and, per folder, how many files were walked and how many folders couldn't be listed.
- **Dedupe links what it can across drives** — a group whose copies sat on different disks was skipped whole. Worse, on an Unraid share or a mergerfs pool every drive reports the same disk, so such a group was never recognised as spanning drives at all, and the script tried links the filesystem could refuse (essentrix83's observation, in issue #17 — measured on the reference setup as one disk reported for three drives). The script now checks the disk itself when it runs and links the copies that share one; where a link fails between the drives of a pooled share, it tries the copies that failed against each other before leaving any alone. On an Unraid share those links generally just work — the share makes each one on the kept copy's drive — so the page shows such groups like any other.
- **Dedupe says what linking a group does, and never promises the bytes** — the page led with **Recoverable**, a figure that could be double the truth for a single group, and selected every group for you. Each group now says whether linking it **repairs a missing hardlink** — a torrent file and a library file holding the same bytes that were never linked (an import that copied, or a copy made by hand), where linking makes the torrent read as imported as well as freeing the space — or removes **duplicate copies**. The headline says how many files would share a copy and how much that frees **at most**, with each file counted once however many paths it has, and nothing is selected for you: which copy is kept is decided by the script when it runs. A group carries a label only when something needs saying — **different disks**, **could not check** (a file auditorr couldn't read, or a copy outside the folder the script runs from), or **changed since the scan** — as a dot and a word, and a group that has changed since the scan can't be selected.
- **The Dedupe script has a dry run, can be run twice, and says what it did** — `bash dedupe.sh --dry-run` checks and compares everything and changes nothing, and a second run reports everything as already linked. Every file gets an outcome — linked, already linked, left alone with the reason, or FAILED, which makes the script exit non-zero — and the summary reports the space actually freed. It says up front how much `cmp` will read (both copies of every file, which on a spinning array can take hours), warns when it was built more than a day before you run it, and refuses to start without GNU `stat` rather than misread a BSD one.
- **Triage rows say more about what they are** — a torrent whose files earned different verdicts says so (`18 files · 3 verdicts`) and takes the verdict whose action deletes least, where it used to take whatever its largest file earned. A row that lists only part of its torrent — a partly imported season shows the episodes that didn't import — says `10 of 18 files · 40 GB of 72 GB`, and the size beside it, and in the selection bar, is the whole torrent's, since that is what removing it removes. When two Sonarr or Radarr instances hold the title (a 1080p and a 4K library, say), the row names both and says which one a rescan or force import goes to — the one whose file matches the torrent's quality — and such a row never pre-selects a whole cross-seed group for removal. Every row shows when your client added the torrent, and **Dead Registration** rows say where the data is still alive: your library, a seeding cross-seed, or both.
- **Triage's live check lists each qui instance once per page** — verification runs in batches, and every batch fetched the full torrent list of every instance involved: a large page on a large qui instance fetched it seven times. It is now fetched once and reused for a minute, and forgotten whenever auditorr removes a torrent.
- **Cleanup leads with what survives a delete, not with how much it frees** — Cleanup is the only workflow whose result can't be undone, and the page sorted by size with **Freed If Deleted** in green: the irreversible deletions came first and greenest, and the one safety fact was a small grey chip. Orphans are now split into **Your library keeps a copy** (lossless — deleting frees nothing and loses nothing) and **This is the only copy** (permanent), oldest first within each, with each file's state beside it and size as a plain readout. Files the last scan couldn't fully check sit under **Could not check**, visible but not selectable. The totals lead with the same split, **Freed at most** is labelled as the upper bound it is, and nothing is ever selected for you. A group that can't take a folder rule says why.
- **Cleanup opens without reading your entire torrent list, and always shows file ages** — the page parsed every torrent file record to show the orphaned few (the same cost Triage shed in v1.7.0), then looked up every orphan's age on disk on every visit, and above 5,000 orphans quietly showed no ages at all. The scan now saves Cleanup's working set separately, with each file's age and link count read once during the scan, so opening the page touches neither the full list nor the disk. A file whose age couldn't be read says **age unavailable** instead of showing nothing. The page falls back to the old way until your next scan.
- **The delete script is safe to run twice, has a dry run, and tidies up after itself** — running a finished script again used to stop with "Cannot find files. Are you in the correct torrent directory?"; a second run now reports everything as already gone and exits cleanly (a genuinely wrong directory is still an error). `bash orphaned_torrents_delete.sh --dry-run` prints what it would do and touches nothing. After deleting a release folder's last file the script removes the folder if it's empty — never a category folder, and never a folder with anything left in it — so emptied release folders stop piling up where no scan will ever mention them. Byte counts no longer depend on `bc`, which Git Bash and some NAS systems lack.
- **Cleanup can exclude release folders saved without a category directory** — a torrent saved straight into your torrent folder has its release folder one level down, and Cleanup refused to write a folder rule for it (the same depth test Triage dropped in an earlier fix). It now uses the same checks as Triage: nothing else lives in the folder, and it isn't shared with your media library.

It now leads with one card, **Grab this one**: the exact replacement on the tracker that sent the PM, pre-selected. If that tracker hasn't listed it yet, the card shows the same release from another tracker and says you'd be cross-seeding it there. Everything else sits under **Other releases** for the cases that need it, and a near match is never selected for you.

It now gets the same follow-through as Backfill: it appears in the import panel at the bottom right (now **Import Jobs**), a stalled import is pushed through for exactly the episodes that were trumped, and the page shows the download's progress. Trumped also finds the Sonarr/Radarr entry from the files the trumped release was imported as, rather than by title alone — and when the files and the new release's name point at different entries, it asks you which rather than picking one.

The grab isn't destructive and no longer needs the setting: **Grab only** grabs the replacement and leaves the old torrents for you to remove in your client. A replacement that's already in Sonarr/Radarr's queue — a double click, or the arr having grabbed it by itself — isn't grabbed twice unless you say so.

It also explains why rows can't be deselected, and what to do if you want to keep one. The total now says the payload is counted once, since cross-seeds share it.
- **Triage and Trumped point at each other** — a dead seed in Triage is often a trump whose PM you missed. Dead-seed rows now carry **Trumped? ↗**, which opens the swap with the release filled in, and the two pages link to each other.
- **Finding matching torrents for a season-pack trump is many times faster** — each trumped episode was compared against every torrent in your client from scratch. Names are now parsed once per request: 20 titles against 5,000 torrents went from about 5 seconds to a third of one.
- **Backfill can offer the release you already have instead of the biggest one** — releases are ranked the way Sonarr and Radarr rank an interactive search: custom format score, then quality, then seeders. That answers "what is the best copy of this?", and it stays the default — it's the order your quality profile already tunes. But it isn't the only question a backfill asks, and the page was already showing everything needed to answer the other one: **Closest to my file** puts first an exact size match, then one within 1% (a scene torrent's `.nfo` and sample make it a little bigger than the video alone), then the same quality, then the same HDR, then seeders. That's the release your file came from, so grabbing it gets you a seed without changing what your library holds. Whichever order you pick, every release now shows its size against your file (`= exact`, `+1.2 GB`) and whether size, quality and HDR agree.
- **A Backfill search survives leaving the page** — the search's only handle lived in the page, so navigating away lost it for good while it carried on querying your indexers for results nobody could see, and starting a search in a second tab silently stopped the first. Backfill now picks a running search back up when you return in the same tab; starting a search while one is running shows you that one instead; a search nobody is watching stops itself after ten minutes; and a finished one is kept for an hour. The progress poll also sends only the rows that finished since the last one, where it used to resend every release for every candidate found so far, every two seconds, for as long as the search ran.

A folder selection saved before this update is ignored rather than quietly filtering your search down to nothing.

Both now open a confirmation listing the rules verbatim, with what they were built from and where they will live. Triage's one-click suggestion chips are unchanged: those already show their rule (`ext:sfv`, `contains:sample`) on the chip itself.

### Bug Fixes
- **Warning boxes, danger buttons and coloured chips on the workflow pages were drawn without their borders** — auditorr tinted colours in a way browsers silently reject, so the rule was thrown away whole rather than drawn faintly. Every yellow warning and red error on Backfill, Cleanup, Triage, Dedupe and Trumped was loose coloured text with no box around it; the destructive buttons — *Generate Delete Script*, *Remove from qui*, *Remove group* — had no outline, so they looked less like buttons than the harmless one beside them; and the coloured chips on a row (*Grab*, *radarr ↗*, *Dedupe ↗*, *Trumped? ↗*, *Failed ↺*) and Backfill's *← New Search* read as coloured words. All of them now draw as designed, and a test keeps the broken spelling out of those pages. The same spelling still appears on a few other pages (the dashboard among them), where it is left for now.
- **Saving Config reset three Rounds tiles to zero until the next scan** — the health score is refreshed from your last scan when you save settings, and that refresh dropped the figures a scan measures but can't rebuild from the file lists: seeding time and your oldest media file. **Atlas**, **Old Faithful** and **Provenance** read 0 until the next scan. Nothing earned was lost — those medals remember their highest point — but the current values vanished. They're kept now.
- **Backfill could report a Sonarr/Radarr instance as healthy when its own read of it had failed** — Backfill read the error list and the root folders separately from the library list, so another page refreshing the same data in between could leave Backfill showing a missing instance with no warning, and folder chips from a list it hadn't used. All three now come from one read, as Triage and Trumped's already do. Closes the last part of the 2026-09-10 outside review.
- **Groups of more than eleven identical files were cut short** — each file remembers at most ten of its identical siblings, and the page took one file's list as the whole group. Fifteen copies of one file became five overlapping groups of eleven: the headline counted more than three times the space there was, and one file could be the copy kept in one group and a copy replaced in another. Groups are now joined from what every file remembers.
- **A duplicate group could change its id between scans** — the id was whichever copy the scan happened to reach first. It is now the group's first path in alphabetical order, which a scan doesn't move.
- **Files sharing only a header and trailer were offered as duplicates** — duplicates are found by size and then a quick fingerprint, which read only the start and the end of each file. Two encodes with the same container header and trailer matched, were counted in the headline and the health score, and were only found to differ when the script compared them in full. The fingerprint now reads the middle too. The first scan after updating may drop a few duplicates from the dashboard and the change log for that reason.
- **A symlink could be replaced with a hardlink** — a symlinked file is read through to its target, so it appeared as another path of the same file, and the script would replace the link with a hardlink, silently changing what that path is. The script now leaves anything that isn't a regular file alone.
- **Triage could confirm an import that never happened** — after **Trigger Rescan**, Triage watches Sonarr/Radarr's own file id and clears the row when it changes. A read that timed out came back looking like a real answer of "no file", which differed from the one before, so the row cleared and the toast said *import confirmed*. A read that fails now counts as "couldn't ask". A Sonarr row also watches **its own episodes** instead of the whole series, so Sonarr importing some other episode of a busy show no longer clears it.
- **Removing torrents cleared rows that were still in the client** — every selected row disappeared on any success, whatever the client actually did (on qui, a request that failed half-way lost the answers for the half that worked). auditorr now looks at your client afterwards: rows whose torrent left go, and a torrent that is still listed, or sits on an instance that didn't answer, stays, marked **removal unconfirmed**, until the next scan.
- **A torrent removed from your client since the last scan stayed on Triage** — marked as verified, with a delete button that removed nothing. It drops as soon as live verification sees it's gone. On qui, a torrent on an instance that didn't answer is never treated as gone.
- **A `.m4v` film was offered as a junk extension** — Triage's *Tidy up* chips treated any video format outside a short list as a sidecar file, one click from excluding it. It now uses the same video list as Backfill.
- **Triage's "Showing the 500 largest torrents" banner** — two separate limits applied, one to torrents and one to dead registrations, only one was reported, and the number in the banner was hardcoded. One limit now covers the whole list, and the banner says how many of how many.
- **Cleanup's "Select all" could read "Select all" with everything already selected** — its label counted every orphan from the scan while the button acted on what was on screen, so after excluding a few rows the two disagreed. Selection is now per pile and per folder, and each checkbox compares against exactly the files it selects.
- **A script that couldn't be built was shown as a script** — an error building a Cleanup or Dedupe script appeared inside the code box as `# Error loading script: …`, where it could be copied or downloaded like one. The dialog now shows the reason instead, with nothing to copy.
- **Removed: generating a delete script over every orphan at once** — `/api/actions/script/orphaned_torrents_delete` without a selection built a script for your entire orphan list, and a second script type, `delete_selected`, did much the same for any paths posted to it. Neither had a button anywhere in auditorr, and both were a one-request "delete everything". The Cleanup script now requires a selection, and `delete_selected` is gone.
- **Trumped could pre-select the release that had just been trumped** — when a release is replaced by its own REPACK, the old and new names differ only by `REPACK`, which the matcher treats as a quality word rather than part of the name. With the PM's tracker chosen, the old release — often still listed there — ranked above its replacement. Only an exact name match can now lead the list or be pre-selected.
- **A trump PM without a "Reason:" line produced an empty list** — auditorr stopped reading the new release name only at a literal `Reason:` line, so a PM without one had its sign-off (or the tracker's own boilerplate) glued onto the name, and nothing matched. A greeting above the release was read as a trumped release too. The name is now one line, and PMs saying *has been trumped by*, *superseded by*, *replaced with* or *has been replaced by* are understood as well as *will be replaced by*.
- **Trumped re-audited seconds after deleting** — that scan recorded the moment between removing the old torrents and importing their replacement, so every swap put a dip in the hardlink score, the health chart and the change log. The audit now runs once the replacement has imported.
- **Editing Trumped's inputs left the old results on screen** — changing a title, the tracker or the new release name after a step had run kept that step's answer, so the tracker preference could reflect a tracker you'd since changed. Later steps now clear when what they were built from changes. Two identical lines in a PM also no longer select and deselect together.
- **Trumped's tracker priority missed trackers named differently between your arrs** — the indexer list is pooled across every Sonarr and Radarr, so one tracker can be `Aither (API) (Prowlarr)` on one and `Aither` on another, and the exact-match check treated those as different trackers.
- **A failed Backfill grab could download the release twice** — any failure to grab, including a timeout on a request Sonarr or Radarr had in fact carried out, triggered a fresh search and a second grab without asking. Only the one failure a new search actually fixes — the release having dropped out of the arr's short-lived search cache — is retried now, and only once; anything else is shown to you as it is. A release that is already downloading in the arr's queue isn't grabbed again unless you click **anyway**, which also stops a second search from grabbing the same thing twice.
- **Backfill couldn't search episodes of daily or anime shows on their own** — searching a single episode needs Sonarr's id for it, and auditorr expected to find that on the file record Sonarr sends, which never carries one. It fell back to reading `S01E05` out of the filename, which a daily show (`Show - 2024-01-05`) or absolute anime numbering (`Show - 087`) doesn't have, so those rows failed with *Could not determine episode ID*. The episode is now looked up in Sonarr's own episode list, by file, which works whatever the naming. It matters more now that a partly seeded season is searched an episode at a time.
- **Excluding a file whose name contains `[`, `*` or `?` either did nothing or hid too much** — exclusion rules built from a real path were matched as glob patterns, and release names are full of glob characters. A path containing brackets — the norm for anime, common in scene releases — became a character class that could not match the very file it was made from, so the row vanished, the toast said success, and the file came back on the next audit with no explanation. A path containing `*` or `?` failed the other way: it matched itself **and its neighbours**, quietly dropping files you never selected out of scoring. Both are closed by a new `literal:` rule that means exactly what it says; every rule auditorr writes for you now uses it. Rules you typed yourself are untouched — if one of them has this problem, it is still there and still visible in Config, because silently rewriting your exclusion list is worse than leaving it.
- **Excluding a partly-imported torrent also hid the files that had imported fine** — Triage lists the files of a torrent that are *not* in your library, and a multi-file torrent was excluded by its common folder. For a torrent where some episodes imported and some didn't, that folder is the release folder, which holds both — so excluding the ones that failed took the ones that succeeded out of scoring with them, and the health score dropped accordingly. Those rows now get one rule per file instead. The **Exclude** action is also gone from *Dead Registration* rows: their paths belong to the healthy cross-seed that is still seeding the same data, so hiding the file would not retire the dead registration and would hide a live file to no purpose.
- **Excluding a season pack saved without a category folder could fail outright** — auditorr decided whether it could write one rule for a whole release folder by counting path segments, on the assumption that segment one is a category directory (`movies/`, `tv/`) and segment two is the release. A torrent saved straight into your torrent directory has its release folder at segment *one*, so that test refused it and fell back to a rule per file — and on a long scene name each of those runs past the 200-character limit and gets refused too. The result was a season pack you could not exclude at all, and a message telling you to select the whole release folder, which was exactly what had just been declined. auditorr now checks what it actually cares about — does anything other than this torrent live in that folder, and is the folder shared with your media library — rather than how deep the folder is. The same pack that produced nine unusable rules now produces one.
- **Clicking Exclude enough times could lock you out of the Config page** — the exclusion list is capped at 100 rules of 200 characters each, and the Config page enforces that on save. The Exclude buttons wrote straight past it. A long path on a nested season pack, or an afternoon of clicking Exclude on a messy library, produced a list the Config page then refused to save — with an error about a rule you never typed, blocking **every other setting on the page** until you found and trimmed it by hand. The buttons now enforce the same limits and say what they refused ("Added 3 of 5 — 2 too long…") instead of reporting a success.
- **A download that was still running was reported as junk** — a torrent at 0% has no library file, which is the literal definition of the *Not Imported* pile, so the newest thing in your client arrived in **Triage** at its full final size with a verdict of **Not in Library** — the bucket that invites a delete — plus a *Trigger Rescan* button pointed at files that don't exist yet. It also counted against the Triage badge and the Rounds card. Nothing on the row could have told you otherwise: `status` wasn't even sent to the page. Torrents your client says are unfinished are now left alone until they finish, and the row carries what the client is doing when there's anything worth saying. One case is deliberately *not* hidden: where your client gave no usable completion figure at all, the row still appears, labelled **completion unknown**, because a row you can see and judge is better than one that quietly vanished.
- **Live downloads could be listed as orphaned and offered for deletion** — "orphaned" means no torrent in your client claims this path, and auditorr worked that out by matching the client's file list against the disk by exact path. Two optional qBittorrent settings break that match while a download is in flight. With *Append .!qB extension to incomplete files* on, the file on disk is `Foo.mkv.!qB` while the client reports `Foo.mkv`. With a separate incomplete directory, the file isn't at its final path at all yet — and if that directory sits inside your torrent folder, auditorr walks files the client's answer doesn't mention. Either way a file being actively written appeared in **Cleanup** at whatever partial size it had reached, and deleting it makes your client error the torrent and start again. auditorr now claims both spellings and follows the client's own answer for where a torrent's data currently is. Neither setting is in the TRaSH layout, so a by-the-guide install was never affected.
- **Release years were being parsed off as file extensions** — a dot-separated release name is the normal case (`Some.Movie.2020`), and auditorr split the year off it the way you would split `.mkv` off a filename, so the year was simply gone. That is the field that stops a 1974 film matching its 2020 remake, and it also affected folder names, which have no extension to take in the first place. Touches every page that reads a torrent path: Backfill, Triage and Trumped.
- **A folder named `HDR` or `DV` labelled every file beneath it** — the HDR badge on library files was detected from the whole path rather than the filename, so one path segment applied Dolby Vision to an entire library branch and the Backfill HDR filters then acted on it.
- **Episodes numbered past 99 resolved to the wrong episode** — the pattern that reads `S01E120` off a filename stopped at two digits and returned episode **12**, which is a real episode, so the release search ran against it and looked like it had worked. Multi-episode files (`S01E01E02`) now try each of their episodes instead of only the first.
- **Backfill merged every oddly-named episode of a show into one candidate** — the season number was read out of the filename, and daily series (`Show - 2024-01-05`), anime absolute numbering (`Show - 087`), `S01.E02` and any non-standard renamer defeated that pattern. Every unparseable episode of a series then collapsed into a single candidate that searched for **one** episode while the row read "N ep". Sonarr reports the season on the very record auditorr already fetches; it now uses it, and the filename is only the fallback.
- **Backfill's "instances that couldn't be read" warning described the page, not the run** — the library list is cached for two minutes, so a search started after a longer spell of setting filters ran against a freshly-fetched library that may have lost an instance since. The warning now also appears on the results, reporting what that run actually saw.
- **Trumped could search and grab against a same-titled item of the wrong type** — matching a replacement release *preferred* Sonarr for something with a season number and Radarr otherwise, but fell back to the other service when the preferred one had nothing. Content type is now a requirement, at every stage of the match, the same way it already is in Triage.
- **Trumped never year-checked a series** — the guard that stops a 1974 film matching its 2020 remake was movies-only, so two series sharing a title resolved on the title alone. It now applies to series too, in the only direction that is sound for TV: nothing can air before the show began. (Long-running and daily series are unaffected — their release names carry air dates, not the year the series started.) Titles that *are* a year — `1923`, `1883`, `2012` — no longer fail their own year check.
- **Trumped told you to add a title your arr was already managing** — when a Sonarr or Radarr instance was unreachable, "no arr knows this release" and "no arr could be asked" produced the same empty answer, and the wizard reported the first. It now says which happened, and names the instance. Trumped also reads the **alternate titles** Sonarr and Radarr hold, so a replacement named in its original language resolves the same way Triage already does.
- **Triage called foreign-language downloads "Not in Library" and invited you to delete them** — a show released under its original-language name (`No.tengo.miedo.S01E01…`) was compared against the English title Sonarr stores it under ("I'm Not Afraid"), matched nothing, and landed in **Not in Library** — the bucket whose description ended *"junk can be deleted"* — for a series Sonarr was actively managing and had already grabbed. Nothing about the row suggested otherwise, and since a not-imported torrent's files are by definition the only copy, acting on it loses the data; that is exactly how one 33 GB season went and had to be re-downloaded. auditorr now reads the **alternate titles** Sonarr and Radarr already hold, which is where every translated and AKA name lives — the arrs have to consult that list themselves to match the grab in the first place, so auditorr was simply not asking. The season above now reads **Import Pending**, with a working *Trigger Rescan* pointed at the right series. Exact titles still take priority, so nothing that matched before changes. **Not in Library's description is also honest now**: it says these files are the only copy and that deleting loses them, rather than implying they're junk.
- **Trumped could delete files out from under torrents that were still seeding** — resolving a trumped release into its cross-seed group starts by asking your client which files the torrent you picked actually holds. If that question failed, the answer came back as an empty list rather than as an error, and an empty list reads identically to "this torrent shares nothing with anything". The group collapsed to the single torrent you selected, the wizard showed you **1 torrent** with no hint that anything had gone wrong, and confirming deleted its files while every cross-seed sibling stayed registered and carried on seeding on top of the hole. It needed nothing unusual to trigger — one timed-out request on a default configuration — and it reported itself as a success. auditorr now stops and tells you it couldn't read the file list, rather than resolving a group it cannot vouch for.
- **A Triage rescan never followed through on Sonarr** — auditorr watches Sonarr/Radarr's own file id after a rescan so the row can clear the moment the import actually lands. The check that reads that id has never worked for Sonarr: it returned a value the API layer couldn't serialize, so the request failed outright. Because the failure was at the very end, a selection containing **both** Sonarr and Radarr items lost its Radarr answers too, and the whole thing was silent — you were told "watching for the import" while nothing was watching, and the row sat there until the next scan. Sonarr rows now clear the same way Radarr rows always have.
- **A TV episode could be matched to a same-titled film, and imported over it** — when Triage decided whether your library already held something, it *preferred* the service that fits the content type but fell back to the other one when the right service had nothing. So an episode of a series your Sonarr doesn't have would match the same-titled movie in Radarr — Fargo, Hannibal, Dune, Shōgun, Parasite; the collisions are ordinary — and report it as **superseded** at the same quality. Same quality is exactly the condition that offers **Force import**, which is Radarr's *Import Anyway* and deliberately overrides every safety check: one click wrote a TV episode over the film. The content type is now a hard requirement, so an episode is only ever compared against Sonarr and a film only ever against Radarr; anything with no match of the right type falls through to *waiting to import* or *not in library*, as it should have.
- **Three of Backfill's five Source filters returned nothing at all** — the *HDTV* chip matched no release on either service, and *WEB-DL* and *WEBRip* matched nothing on any TV candidate. Backfill was comparing against a raw internal field that Sonarr and Radarr spell differently (`web` vs `webdl`, `webRip` vs `webrip`, `television` vs `tv`), so the filter quietly excluded everything. Nothing said so — the candidate simply came back with no release found, which looks exactly like no release existing, so narrowing to WEB-DL on a TV library gave you a page of dashes and every reason to suspect your indexers. The chips now read the quality name both services agree on, which is the same thing the rest of auditorr already uses.
- **Trumped stopped auto-matching whenever a release was named without a group tag** — it identifies the encode by the tag after the final hyphen, and took `WEB-DL` and `Blu-Ray` at face value: a torrent named `…AMZN.WEB-DL` was read as belonging to a release group called "DL". When the PM named a real group and your copy of the same payload didn't, the two disagreed and the correct torrent was disqualified outright — no pre-selection, and the one row left carrying a red *group* mark that misstated the reason. The reverse was quieter: two releases with no group at all both reduced to "DL" and were scored as *agreeing* on a group neither one declared. Quality tokens are no longer mistaken for release groups.
- **Backfill kept showing pre-scan results while you had it open** — every other workflow page reloads itself when a scan finishes; Backfill loaded once and never again. So its candidate list, folder chips, Search Depth line and Generate count stayed frozen at whatever the last scan said when you opened the page — including across the scan **your own backfill just caused**. A file you had successfully backfilled was still offered as a candidate, and grabbing it again is simply downloading it twice. It now refreshes with the others.

A Sonarr season pack counts as its episodes, because the ladder counts files. ### Bug Fixes
- **Backfill grabs could score nothing at all** — Matchmaker credit was awarded by the background job that follows a grab into your library, which meant the points depended on that job surviving the whole download. Restart the container while something is downloading — a version update, say — and the grabs in flight scored zero, even though every one of them imported perfectly a few minutes later. A stalled import you then finished by hand didn't count either. Credit is now recorded when the grab is accepted, which is the part auditorr can actually vouch for; the import watch carries on doing its job and reporting honestly, it just doesn't hold the scoreboard. **Grabs already lost this way can't be recovered** — nothing on disk records that they happened.
- **A prize credited while a scan was finishing could vanish** — trump swaps and backfills are counted the moment they happen rather than at the next audit, and the audit wrote the whole progress record back from a copy it had taken moments earlier. Anything credited in that window was overwritten and gone for good, since these counters only ever add. The odds aren't as long as they sound: auditorr scans right after the filesystem change an import causes, so the two events cluster. Both now write through the same lock, and the audit merges rather than overwrites.
- **Acting on a workflow row now shows up everywhere, straight away** — you'd delete a torrent in Triage, watch the row disappear, and then notice the sidebar badge hadn't moved; navigate away and back and the row you just dealt with was sitting there again. Every workflow report and the Rounds page are built from the last audit, so until a new one ran the server kept handing back the same answer. Three things were wrong and all three are fixed: pages left open during a scan now update themselves when it finishes, rather than showing pre-scan data until you navigated away; rows you've acted on stay gone if you leave the page and come back; and the actions that change something **auditorr can't see on disk** — removing a torrent while keeping its files, or adding an exclusion — now schedule an audit themselves, where previously nothing did until the next scheduled one hours later. That audit is debounced, so working through twenty rows still costs one scan, and it waits for you to finish rather than scanning while you're mid-session. The **Refresh buttons are gone** from Cleanup, Dedupe and Triage: a refresh button on a page built from the last audit is a stale page with a button, and on Triage it was actively misleading — it re-read the same stored data.
- **A Triage rescan looked like it did nothing** — the rescan hands your file to Sonarr/Radarr, which imports it whenever it gets round to it and reports nothing back, so the row just sat there. auditorr now watches the arr's own file id and clears the row the moment the import actually lands, usually within a few seconds. Rows it can't watch — anything with no matching library entry — are marked *rescan sent* instead of looking untouched.
- **Three prize ladders were secretly the same ladder** — Packrat, Tidiness and Purity all started from the total size of your torrent directory and differed only by subtracting the orphaned or not-imported bytes. Those are the health score's penalty terms, so on any library in reasonable shape they're a couple of percent, against ladder rungs that sit 2–2.5× apart. The three tiles therefore showed the same value and tiered in lockstep forever: *Geological Layer*, *No Dust Exists Here* and *Twice Distilled* all unlocked at the same instant, and "No Dust Exists Here" was really being awarded for owning 10 TB. Tidiness and Purity now measure how large your torrent directory was **on a day when the relevant pile was actually empty**, so a spotless 5 TB library outranks a filthy 500 TB one until it sweeps. Nothing is taken away: the ladders latch on your best-ever value like every other prize, so any rung you already hold stays held — it simply won't advance again until the library is genuinely clean.
- **Adding a second Sonarr/Radarr silently switched off your first one (#22)** — the *Additional Sonarr/Radarr instances* list didn't add to the primary Sonarr and Radarr fields above it, it **replaced** them. Adding a single extra instance — a 4K Radarr, an anime Sonarr — retired your main pair completely, while their fields stayed on the Config page, kept saving, and kept answering "Connected and saved!" when tested. Nothing read them. Everything that depends on Sonarr/Radarr went with them: Backfill could only offer candidates from the extra instances (which is how this was found — a library with four instances showed one root folder), Triage lost the library comparison that separates a superseded torrent from an unknown one, and deep links, indexer lists, rescan and force import all saw a fraction of the library. **The two are now merged**, so if you are affected, upgrading is the whole fix — no configuration change, nothing to re-enter. An instance listed in both places is still only read once. Expect your counts to move on the first scan after upgrading, and if one of those primary fields has been pointing at a dead host for a while, you'll now hear about it.
- **Backfill merged shows across two Sonarr instances (#22)** — candidates were grouped by series id and season alone, but series ids are per-instance: both your Sonarrs number their first series `1`. Two unrelated shows that happened to share an id collapsed into a single candidate, and the survivor kept its own instance — so the absorbed show's episodes were never searched, and the release search that did run went to the wrong Sonarr for the wrong series. The grouping key now includes the connection, so each instance's shows stay their own candidates. Movies were never affected (Radarr candidates aren't grouped).
- **Backfill's candidate count was divided by a number it has nothing to do with** — the *Search Depth* line read like `15 searchable candidates (2612 total unseeded)`, which invites you to read the first as a fraction of the second. It isn't one, twice over. A candidate is a **group** — one Sonarr season is a single candidate however many episodes it holds — while the total counts individual **files**; and the total counts *every* file, including subtitles, NFOs, artwork and extras, none of which Sonarr or Radarr indexes and none of which could ever match. So a perfectly healthy library reported what looked like a catastrophic gap, which is exactly what happened while diagnosing #22 and cost a round of back-and-forth to rule out. The two are now stated as separate facts, with the noun in front of the numbers: `15 searchable candidates. Of 2612 unseeded files, 412 matched your Sonarr/Radarr library.` That second sentence is the one that actually answers "did auditorr find my library", so it now also appears when **nothing** resolved — previously the whole line was hidden in the one case where you most needed to see it.
- **Rounds called Backfill blocked when your arrs were only in the additional-instances list (#22)** — the page asked those connections for a `url` field, which the Config page does not write (it writes `base_url`), and never checked for an API key at all. If your Sonarr and Radarr live only in *Additional Sonarr/Radarr instances*, with the primary fields above left blank, Backfill sat on *Blocked — connect Sonarr or Radarr* against two perfectly good instances, and the *Connect Sonarr* and *Connect Radarr* setup steps never ticked no matter what you did. Rounds now asks the same question every other feature asks, of the same function, so there is one answer to "which arrs are connected" rather than a second one on this page.
- **One unreachable series discarded an entire Sonarr library** — Sonarr needs an API call per series where Radarr needs one in total, and a single failure among hundreds aborted the whole instance's file index. To everything downstream that looked identical to a Sonarr managing nothing: its files stopped resolving, its titles vanished from the Backfill folder list, and Triage lost the library comparison that tells a superseded item from an unknown one. A series that can't be read is now skipped and logged, and the rest of the library comes back.
- **Library listings could time out on large instances** — the full `/api/v3/movie` and `/api/v3/series` responses were fetched on the 10-second timeout that suits single-item calls. On a big library that is not a comfortable margin, and exceeding it produced no visible error — just an instance that appeared to manage nothing. Those two bulk listings now get 60 seconds; nothing else changed.
- **A Sonarr/Radarr instance that failed to load said nothing** — if auditorr couldn't read an instance, its files silently fell out of Backfill, taking their entries in the *Root Folders* list with them, and the page gave no hint that anything was missing. Backfill now names the instances it couldn't read and says plainly that everything they manage is absent from the list below.
- **Test Arr Connections withheld the answer it had** — the check already collects a sample library path from each instance, which is the one thing that shows whether auditorr sees your files where your arr says they are, and the page threw it away. Each instance now shows a sample path under its result, along with the reason when one connects but its library can't be read.

### Known issues
- The *Root Folders* list on Backfill is derived from the first path segment below your `MEDIA_PATH`, not from the root folders configured in Sonarr/Radarr — auditorr doesn't read those. It is right for the common layout (`/data/media` holding `movies`, `tv`, `anime`), but root folders nested deeper than one level collapse into a single entry, and only folders with a searchable candidate in them appear at all.

- **Force import in Triage** — a new action on superseded items that replaces the file Sonarr/Radarr already holds, using their own "Import Anyway" mechanism (`ManualImport` with `replaceExistingFiles`). Trigger Rescan can never do this: the arr evaluates its upgrade and revision specs against the existing file and refuses anything not strictly better, which a same-quality trump replacement never is — a non-REPACK over a REPACK is rejected as "not a quality revision upgrade" no matter how many times you rescan. Offered **only** where the torrent scores the same quality as the library file. A genuine downgrade (1080p against a 2160p library file, WEB-DL against a Bluray) simply doesn't get the action — those rows already sit under a "lower than library" heading that explains why, and refusing them is correct behaviour rather than a bug to work around. If you ever do want one of those in your library, Sonarr/Radarr's own Manual Import is the right place for it: one deliberate file at a time, rather than a bulk selection.

### Bug Fixes
- **Trumped could offer a release for a completely different title** — matching scored quality agreement (resolution, source, release group, audio) alongside the title, so two unrelated releases that merely shared a format could out-score a real match: a 2019 film was offered as the replacement for a 2026 one because both were 1080p WEB-DLs. The title is now a **gate, not a score** — the two title cores have to genuinely overlap and the year (±1, for premiere-vs-release-year renderings) and season/episode anchor have to agree, or the candidate is dropped entirely. Quality only refines the ranking *within* real title matches, and where nothing genuinely matches the picker now says so and offers manual entry or the Sonarr/Radarr deep link, instead of a confident wrong answer. The same gate now covers the pre-selected torrent match, which had its own ungated path — that one was offering a 2025 release for a 2026 trump notice. Punctuation is also folded before quality tokens are stripped, so `HDR10+` is no longer counted as a word in the title.
- **Triage's sidebar badge disagreed with the Triage page** — the badge counted *files* flagged not-imported or dead, which is neither what the page lists nor how it lists it. Dead registrations were invisible to it (a page of 10 items showed a badge of 4), while a not-imported season pack counted once per file — 20 rows for one torrent. The badge and the Rounds Triage card now count items the way the page groups them, per torrent.
- **Trigger Rescan reached the wrong folder** — the rescan pointed Sonarr/Radarr at the *parent directory* of the file, but the arrs identify a release by parsing the folder name they are given. For a single-file torrent sitting in its category dir that meant handing over the download root: Radarr parsed "radarr" as the release name, logged `Unknown Movie`, and imported nothing. A nested season pack handed over "Season 1", which parses no better. The scan now targets the **release folder** — the second segment below the torrent root — and falls back to the file itself when there is no release folder, which both arrs accept and parse from its own filename.
- **Rescan could move a file out from under a seeding torrent** — the scan command sent no `importMode`, so the arrs used their default of `Auto`, which means *move* whenever no download-client item is attached to the scan. One never is for a Triage rescan, by definition: it exists for payloads the arr never grabbed. The import mode is now sent explicitly as `Copy` — the arr's name for "leave the source in place", and the only mode that consults the *Use Hardlinks instead of Copy* setting, so a successful import costs no extra disk and the torrent keeps seeding.
- **Manual-import lookups asked Sonarr/Radarr the wrong question** — auditorr scoped its `/api/v3/manualimport` folder lookups with `movieId`/`seriesId`, which reads like a filter but isn't one: the arr ignores the folder entirely and returns that item's **existing library file** instead of the folder's contents. Every folder-based lookup therefore came back describing the file being replaced rather than the one to import. The item is now forced in the import command itself, where it belongs, and the lookup is left to answer what it was asked. This also fixes the Trumped workflow's folder fallback, which had been silently affected since it shipped — trump only kept working because its download-id lookup answers first.
- **Single-file torrents couldn't be identified for import** — a lookup pointed at a torrent's *containing* folder lands on the shared category directory, and Sonarr/Radarr only parse a title when they can anchor on a release folder name: every file in that listing comes back with no movie and quality "Unknown". Lookups now target the release folder when there is one and the file itself otherwise — both accepted — so quality, language and release group are read correctly instead of being imported as Unknown.
- **A rescan the arr refused reported success anyway** — Sonarr/Radarr report every scan command as `completed` whether it imported everything or rejected everything, so a refused rescan surfaced as a green "Rescan triggered" toast and looked like a mystery. auditorr now asks `/api/v3/manualimport` what the arr would decide — the same specs, reported per file — and shows the real reason ("Not an upgrade for existing movie file", "Not a quality revision upgrade"). Failing to check is kept distinct from checking and finding no objection, and a file the arr can't identify at all is reported as such rather than passing silently.

### Improvements
- **arm64 images** — `ghcr.io/thrill-burn/auditorr` is now published for `linux/arm64` as well as `linux/amd64`, so it runs natively on a Raspberry Pi 5, an ARM NAS, or Apple-silicon Docker without emulation. The Python dependencies are pure Python, so nothing compiles under QEMU during the build; the frontend stage is pinned to the build host's architecture, since Vite's output is identical on every target and building it natively keeps the arm64 image from paying for an emulated `npm` run.

## v1.7.1 — 2026-08-01

A security release. No feature or UI changes — a no-secret LAN install behaves identically after upgrading.

### Security
- **Non-local API access is now closed by default (#18)** — previously an empty `AUDITORR_SECRET` disabled authentication entirely, leaving the full administrative API (results, config, workflows, client deletes) open to anyone who could reach the port, including the internet on a port-forwarded install. With no secret configured, auditorr now serves **local clients only** — loopback and private ranges (10/8, 172.16/12, 192.168/16, IPv6 ULA and link-local) — and answers everything else with a generic 401 that doesn't reveal whether a secret exists. Locality is judged by the connection's source address, never `X-Forwarded-For`, which is attacker-controlled and would let a remote client spoof a private address. A configured `AUDITORR_SECRET` is still enforced for every client, local ones included.
- **The `?secret=` query-string fallback was removed** — the access key is now accepted **only** via the `X-Auditorr-Secret` header, because query strings leak into reverse-proxy access logs and browser history. The web UI already used the header; any bookmark, script, or `curl` invocation passing `?secret=` must be switched over.
- **New — `AUDITORR_TRUSTED_NETWORKS`** — comma-separated CIDRs treated as local in addition to loopback and private ranges, e.g. `100.64.0.0/10` for Tailscale (CGNAT space, not RFC1918, so the built-in private-range check does not cover it). Invalid entries are logged and skipped rather than failing startup.
- **New — `AUDITORR_REQUIRE_AUTH=true`** — strict mode: the key is required even from local clients, with no local exemption at all. Set without an `AUDITORR_SECRET`, it fails closed rather than running open: every `/api/*` route returns 503 `auth_not_configured`, and the UI replaces the page with a setup notice that clears itself as soon as a secret is configured and the container restarts.
- `/health` and the static SPA shell stay open, so container health checks are unaffected. `docker-compose.yml` and the Unraid CA template (`auditorr.xml`) document the new model; the debug report records `auth_strict` and the trusted-network count (never the networks themselves).

### Upgrade notes
- **Nothing to do** for the common case — a LAN install reached from LAN clients, with or without a secret set.
- **Set `AUDITORR_SECRET`** (a long random value) if you reach auditorr from outside your LAN — port forward, VPS, or a remote host — or add your tunnel's range to `AUDITORR_TRUSTED_NETWORKS`. Without one of the two, those requests now get 401.
- A reverse proxy running on the **same host or LAN** as the container passes the local check, because the proxy's address is what gets evaluated. The local-only default cannot see past a proxy — if the proxy itself is internet-facing, set `AUDITORR_SECRET` or enforce authentication at the proxy.

## v1.6.1 — 2026-06-10

### Features
- **`/api/debug/report` diagnostic endpoint** — returns a privacy-scrubbed JSON dump designed to be pasted publicly when reporting issues: runtime info (current/peak RSS, container memory limit from cgroups), sanitized configuration, library and database size stats, scan state with per-phase memory history, crash evidence, the last 20 audit runs, and the last ~400 log lines. Credentials are never included; hostnames, IPs, and API tokens are redacted; media file and folder names are replaced with stable 6-char hashes (`~a1b2c3.mkv`) so files can be correlated across the report without being readable. Generic structure (`/data/torrents`, `Season 01`, real file extensions) is preserved for debuggability.
- **Aborted-scan detection** — the audit now writes a scan marker at start, updates it at every phase with current memory usage, and removes it on any normal exit. If the process dies mid-scan (OOM-kill, container restart), the next startup finds the marker and records an **aborted** entry in Audit History stating exactly which phase the scan died in and how much memory it was using. Previously a killed scan left no trace at all — the audit history stayed empty and the scan silently restarted from the top.
- **OOM kill attribution** — an OOM kill is a SIGKILL, so nothing can be logged at the moment of death; instead the kernel's per-cgroup `oom_kill` counter (which survives worker restarts) is checked at boot. If it incremented since the last boot, the aborted-scan entry says "confirmed out-of-memory" rather than "probably". A memory sampler thread also runs during scans: it persists an RSS reading into the scan marker every 20 s (so a killed scan shows memory from seconds before death, not just the last phase transition) and logs warnings while there is still time to read them — at 85% and 95% of the container memory limit, or when host available memory drops below 400 MB with no limit set. Python-level `MemoryError` is now caught explicitly: the scan structures are freed first so the error itself can be logged and persisted with clear out-of-memory wording.
- **Background-thread crash logging** — unhandled exceptions in background threads (audit, watchdog, workflows) previously printed to stderr only; they are now routed through logging so they appear in the debug report's log buffer. `faulthandler` is enabled so native crashes (SIGSEGV) dump Python tracebacks to the container log. Boot logs a one-line memory summary (RSS, container limit, host available, cgroup oom_kill count), and scan completion logs file/tracker counts, duration, and final RSS.

### Bug Fixes
- **Crash-restart scan loop on very large libraries** — on 500K+ file libraries the scan could be killed mid-run (out-of-memory or gunicorn worker timeout), which left no audit history entry and immediately re-triggered the startup audit when the worker respawned — appearing in the UI as the scan endlessly starting over even with the watchdog disabled. Three fixes combine to address it:
  - **Duplicate detection memory blowup** — for a group of *k* identically-sized identical files, every file stored all *k−1* sibling paths: *k²* path strings total. Disc-based libraries (BDMV/DVD rips) contain thousands of identically-sized structural files (`.bdmv`, `.clpi`, `.mpls`, plus the `BACKUP` copy inside every disc), producing groups large enough to consume many GB of RAM and inflate the stored `files_json` — likely also the root cause of the earlier "string or blob too big" failures. Size groups larger than 200 files are now skipped (real media duplicates come in groups of 2–5), each file stores at most 10 sibling paths, and **excluded files are skipped entirely** — previously an excluded disc directory was still hashed and cross-referenced, so exclusions did not reduce duplicate-detection cost at all.
  - **Diff no longer loads previous file lists** — computing the change log deserialized both previous full file lists (several GB of Python objects at 650K files) while the current lists were also in memory. Each audit now saves a compact `{path: bitmask}` signature map per tab (~2% of the size) and the next audit diffs against that. Diff lists are capped during collection, so a mass rename can't transiently allocate one entry per file. The first audit after upgrading skips the change log entry once while signatures are established.
  - **Crash-loop breaker** — after 2 consecutive scans killed mid-run, the startup audit and watchdog are paused and a clear warning is shown instead of hammering the disk for hours on every container restart. A completed manual scan re-enables automatic scanning.
- **gunicorn worker killed by slow requests** — the Docker image now runs gunicorn with the `gthread` worker (8 threads) instead of the default sync worker. Previously a single slow request (e.g. serving a very large `/api/files` response) could exceed the 300 s timeout and get the worker SIGKILLed — taking any in-progress audit down with it — and blocked all other requests (including progress polls) while it ran.
- **Generated scripts now respect Excluded Files & Folders** (#14) — excluded files are invisible to script generation: the orphaned-cleanup script no longer emits `rm` commands for excluded orphans, and the dedupe script skips excluded files both as the canonical copy and as duplicate partners (a group whose only partners are excluded is dropped entirely, so the script never hardlinks over an excluded file). Script headers report how many files were skipped due to exclusions. Previously users had to hand-edit generated scripts to remove excluded entries — and the delete script would have removed intentionally-kept files (e.g. DVD rip metadata).

### Performance
- **Dedupe script verifies with `cmp` instead of `md5sum`** — `cmp -s` stops at the first differing byte, while `md5sum` reads (and hashes) both files in full even when they differ immediately. For a false-positive pair of large remuxes that's a few KB of reads instead of the combined file sizes; identical pairs cost the same I/O minus the hashing CPU. Also matches the relink workflow, which already verified with `cmp`.
- **`/api/files` streams stored JSON** — the endpoint previously parsed the stored file list (`json.loads`) and re-serialized it (`jsonify`); at 650K files that costs minutes of CPU and several GB of RAM per request. The stored JSON is now streamed straight through in decompressed chunks without ever being parsed.
- **Config save no longer deserializes huge libraries** — saving settings recomputes health metrics from stored file lists so threshold changes apply instantly; for libraries above 200K files this is now skipped (new thresholds apply on the next audit) instead of loading both full file lists into memory on every save.
- **Granular scan phases with memory telemetry** — "Computing health metrics" previously covered six internal steps including diff computation and database saves. Each step now reports its own status message and logs process RSS at every transition, so slow or crashing scans can be pinpointed to an exact step.

## v1.5.0 — 2026-05-22

### Performance
- **Large-library memory usage** — four changes combine to reduce peak and sustained RAM for libraries with hundreds of thousands of files. Users previously reported 8 GB of Docker memory usage after 24 hours; the root causes were all in the backend:
  - **Early release of scan intermediates** — `torrent_records`, `media_records`, `inode_map`, and `duplicate_map` are explicitly deleted after `_assemble_records()` so Python's GC can collect them before subsequent allocations. A new `/api/files?tab=media|torrents` endpoint and `file_results` table serve them on demand. The frontend fetches them lazily only when the user navigates to the File Explorer or Trackers tabs. - **Torrent hash stored per file** — hash is now captured from qBittorrent and stored in results, enabling future deep-link and per-torrent features.
- **Normalized title matching** — Sonarr/Radarr library search strips punctuation before comparing, fixing matches for titles with colons, dashes, and other special characters.
- **Rescan path translation** — Sonarr/Radarr rescan commands translate auditorr-local paths to the correct path as seen inside the arr container.
- **set -euo pipefail removed from delete script** — per-file existence checks handle errors gracefully without aborting the entire script on first failure.

### Frontend
- **Script modal** — full-screen overlay for reviewing generated bash scripts before running. Shows warning banner, scrollable monospace script, copy to clipboard, and download as .sh.
- **Smart Sonarr/Radarr button visibility** — buttons only shown for relevant file types based on path detection, not on every orphaned file.
- **Action button rows** — consistent two-row button layout across all dashboard cards, aligned left-to-right.
- **Recoverable size** — orphaned torrents card shows total recoverable GB in the same style as duplicate files.
